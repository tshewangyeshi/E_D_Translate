## Requirement ID convention used in this doc

The only file in the folder, `01-srs.md`, is written as repo guidance (invariants, domain facts, stack, rules). It cites eight requirement IDs but does not define a numbered requirement list. This doc therefore:

- cites only those eight IDs, with the meaning taken from the invariant each is attached to: **FR-140** (entities byte-identical), **FR-150** (cache keys include model + glossary version), **FR-160** and **FR-330** (render-time artefacts never in cache / TTS input), **FR-210** (widget mutates `nodeValue` only), **FR-510** (Tier 1 never live-translated), **NFR-410** (fail open to English);
- marks every other requirement it introduces as **UNNUMBERED**. Nothing here invents an ID. Numbering happens in the SRS, not in this doc.

## Problem Statement

Bhutanese government websites are published in English, and many citizens read Dzongkha more comfortably than English. dzweb is a service any government site can call to show its pages in Dzongkha. It wraps GovTech's existing NLLB-based NMT model (served via WSO2: slow, rate-limited, occasionally down) and does not train models.

v1 targets **one citizen services portal**: forms, fee schedules, eligibility rules, citizen IDs and file reference numbers on nearly every page. That is the hardest realistic pilot, because a wrong digit in a fee or an ID is a citizen-facing defect, not a style issue.

Read-aloud (TTS) is **deferred to future work** by decision in this session. v1 stays TTS-ready (see Premise 1).

## What Makes This Cool

Every existing website translator either translates each DOM text node in isolation (garbling sentences, especially for a verb-final language like Dzongkha) or rebuilds the DOM (Firefox Translations wraps each word in `<font>`; commercial widgets replace nodes), which crashes React and Vue host pages.

dzweb does neither. It translates **whole blocks** with tags and entities swapped for checked placeholders, then pours the result back into the **same text nodes** via `nodeValue`. Integrity is checked deterministically, not hoped for. When a translation can't be written back without changing the node structure, that block stays English, and the system counts why. A citizen never sees a wrong number, a broken page, or a crashed form.

The second payoff: every human-approved Tier 1 translation becomes a versioned English–Dzongkha government parallel corpus entry, so real citizen traffic decides what gets reviewed, and GovTech gets measurable data to improve the model it already owns.

## Constraints

- Stack is fixed: Python 3.11 / FastAPI orchestrator; PostgreSQL (translation memory, audit); Redis (hot cache); S3-compatible storage (reserved for future audio); TypeScript widget with no framework and no build step, **< 15 KB gzipped**, must run on a five-year-old Android device.
- Upstream NMT via WSO2 is slow, rate-limited, and occasionally down. It has never seen HTML and deletes, duplicates or invents tags.
- Dzongkha (Tibetan Uchen script): no inter-word spaces; tsheg `་` U+0F0B separates syllables; shad `།` U+0F0D / double shad `༎` U+0F0E terminate sentences; stacked glyphs need `line-height` ≈ 2.0 and ≈ 1.3× Latin font size; browser line-breaking is unreliable.
- Public-sector infrastructure serving unauthenticated traffic. Live threats: SSRF, XSS through re-injected translations, cache poisoning. `/cso` before every release.
- Tests: `pytest` + `vitest`. Entity-preservation and tag-integrity suites are ship gates. `tests/fixtures/gov-pages/` is read-only golden data. Synthetic IDs only, from `tests/fixtures/synthetic-entities.json`. No real citizen data in any session.
- `make check` = lint, type check, both unit suites, both gate suites.
- `orchestrator/pipeline/` is guarded (`/guard`) because it holds entity masking and tag restoration.
- Telemetry off on this machine (verified 2026-09-16 via `gstack-egress grants`: all outbound channels off).

## Premises (agreed)

1. **v1 is English → Dzongkha text translation only.** Read-aloud is future work, but the text pipeline stays TTS-ready: zero-width spaces and any other render-time artefacts exist only in the widget's DOM writes, never in cache, TM, or anything a future TTS stage would read (FR-160, FR-330).
2. **One citizen services portal first, integrated by a single `<script>` tag.** Portal authors mark Tier 1 content with `data-dz-tier="1"`, which the server treats as a hint it can only raise; a server-side per-origin tier rule set is authoritative (revised during spec review). The orchestrator receives text segments, **never URLs**, and never fetches pages server-side. This removes the SSRF surface a proxy design would have.
3. **Tier 1 = legal / eligibility / fee terms, served only from human-approved translation memory.** No approved entry → that block stays English with a Dzongkha "official translation pending" notice, and the request enqueues the segment for human review. Live MT for Tier 1 is rejected in code (FR-510).
4. **Revised after cross-model challenge: two placeholder classes, one integrity validator.** Blocks are translated whole.
   - **Entity placeholders** (numbers, dates, currency, citizen IDs, file refs, emails, URLs): must each appear exactly once and be restored byte-identical (FR-140). They may move anywhere *within the text run they belong to*.
   - **Tag placeholders** (inline element boundaries): must each appear exactly once and in the **original order**, because `nodeValue` writes cannot reorder nodes (FR-210).
   - Any violation → the block stays English (NFR-410), and the cause is recorded.
   - The fallback rate is measured on real pilot content in Phase 0 **before** infrastructure is built (see Phase 0 gate).
5. **Only the eight cited IDs are confirmed requirements.** Everything else is UNNUMBERED until the SRS assigns IDs.

## Approaches Considered

- **A: Harness + thin slice** (widget, pipeline, Redis cache, Tier 1 always English, no TM/review). Rejected: contradicts Premise 3 (Tier 1 content would never become Dzongkha) and every model change would flush all translations.
- **B: Full v1 platform, synchronous** (cache miss calls MT live under a timeout budget). Not chosen as-is: first visitors' page loads would wait on the slow upstream.
- **C: Async translate-behind without reviewer UI.** Not chosen alone: leaves Tier 1 permanently English.
- **Chosen: B + C's async miss path**, preceded by the Phase 0 harness. Detailed below.

## Recommended Approach

### Architecture overview

 └───────────────────────────┘                                │             │
                                                     Redis hot cache   PostgreSQL

### Phase 0: Fixture harness and go/no-go gate (before any infrastructure)

1. Obtain ~20 public page snapshots from the pilot portal into `tests/fixtures/gov-pages/` (read-only once committed). Any real personal data found is replaced with values from `synthetic-entities.json` before commit.
2. Write the **widget's real** block extractor and tag-placeholder encoder in TypeScript; run under jsdom in vitest. This is shipping code, not throwaway.
3. Write the Python entity masker and placeholder validator in `orchestrator/pipeline/`.
4. Send each masked block to the WSO2 NMT **once** (dev credentials, content limited to the public snapshots), recording raw responses to `tests/fixtures/mt-replay/` keyed by source hash + model version. All later tests replay these, so CI never calls upstream.
5. Try at least two placeholder token formats (e.g. bracketed numeric tokens vs. XML-like self-closing tokens) and record which one NLLB preserves best. UNNUMBERED.
6. Hand-label the entities in the snapshots (a labelled copy alongside the golden data, not edited in place). Tune masker patterns on 15 pages; **hold out 5 pages** for measuring recall. Draft a small glossary (portal service names, fee/eligibility terms) and run the glossary check, so its miss rate is measured before it becomes a production fallback cause.
7. Produce a report: block fallback rate overall, **by cause** (entity lost / entity altered / entity duplicated / tag lost / tag duplicated / tag reordered / text in non-existent run / glossary term missing / leak scan hit / upstream error) and **by block type** (heading, paragraph, paragraph-with-link, table cell, form label, list item).

**Gate:** all three must hold before Phase 1 (thresholds UNNUMBERED, to be confirmed with GovTech):
- **Masker recall = 100%** against the labelled entities on the held-out pages. An entity the masker misses goes to the model unprotected, which the validator cannot detect.
- **Leak scan = 0:** an independent scan of every *validated* output finds no digit (ASCII or Tibetan U+0F20–U+0F29), ID pattern, email or URL outside restored entity placeholders. This catches numbers the model invents or converts.
- **Block fallback ≤ 20%** (proposed). If tag-reorder dominates the fallback, revisit before Phase 1. Candidate remedies, in order of preference: route those blocks to the review queue so an approved TM entry can supply a structure-compatible translation; split the block at the offending inline boundary and translate the parts separately; never DOM restructuring (FR-210 stands).

### Phase 1: Widget (`widget/`)

- Loaded as `<script src="https://<cdn>/dz/v1/dz.<hash>.js" defer integrity="sha384-…" crossorigin="anonymous">`. Versioned, immutable file; SRI hash published per release. UNNUMBERED.
- **DOM ownership rule (FR-210 scope):** inside host-owned blocks, the widget only writes `nodeValue` of existing text nodes; it never creates, removes, replaces or moves nodes there. The widget owns exactly two things it may create: one stylesheet in `<head>`, and one widget container (toggle + status line) placed in a portal-provided `data-dz-toggle` element or appended to `<body>`.
- Toggle choice remembered in `localStorage`, wrapped in try/catch; works without it.
- **Tier 1 pending notice:** shown once, in the widget container's status line ("some official text is shown in English while its Dzongkha translation is reviewed", in Dzongkha), never inside host blocks.
- **Block extraction:** block-level elements (`p, li, td, th, h1–h6, label, dt, dd, caption, figcaption, button, summary, legend`). **Innermost block wins:** a block element containing another block element contributes only its own direct text runs outside the nested block (e.g. `li > p`: the `p` is the block). Text of an outer block on each side of a nested block becomes **separate segments**, one per contiguous stretch. Skips `script, style, code, pre, textarea, noscript, [translate="no"], [contenteditable], [data-dz-skip]`, and form control values. `data-dz-tier` is read from the nearest ancestor (default Tier 2) and is a **hint the server may only raise** (see tier authority). UNNUMBERED.
- **Segment encoding:** a block is serialized as its text nodes in document order, with a tag placeholder pair around the text of each inline element. Rules: adjacent text nodes are separate runs; whitespace-only text nodes are kept as runs but not sent for translation (written back unchanged); void/empty inline elements (`<br>`, `<img>`, empty `<span>`) become a single self-closing marker so order is still checked but no run is created; a run position with no underlying text node is a **slot-less position**. The validator rejects any output that puts non-whitespace text into a slot-less position (cause: *text in non-existent run*). **Marker formats:** on the wire, tag markers are `⟦tN⟧…⟦/tN⟧` and void markers `⟦vN/⟧`; the server adds entity placeholders `⟦eN⟧` during masking. Only the server converts wire markers to the model token format chosen in Phase 0 and back; delimiter un-escaping happens after the model call and validation. Before encoding, the placeholder delimiter characters `⟦` `⟧` in source text are escaped (`⟦⟦`, `⟧⟧`), and the server rejects blocks containing unescaped delimiters or malformed markers.
- **Write-back (FR-210):** the orchestrator's text is split at tag markers into runs; run *i* is written to text node *i* via `nodeValue`. A `WeakMap<Text, string>` keeps the English original for toggling back.
- **Render-time line breaking (FR-160):** after each tsheg `་`, the widget inserts U+200B **only in the string it writes to `nodeValue`**. The originals map and anything sent back to the server contain no U+200B.
- **Typography:** the stylesheet targets `[data-dz-on]` blocks with the DDC Uchen font stack, `line-height: 2`, font-size ≈ 1.3×. The widget sets `lang="dz"` and `data-dz-on` **on each block element it actually translated** (attribute writes, not node changes), and removes them on toggle-back or fallback. English fallback blocks keep Latin typography. Because styles inherit, every block the widget handles also gets `data-dz-block`, and the stylesheet (a) sizes translated text from a custom property `--dz-base` holding the block's original computed font size, captured before the first write, so nested translated blocks never compound 1.3 × 1.3; and (b) resets handled-but-untranslated blocks with `[data-dz-block]:not([data-dz-on]) { font-family: revert; line-height: revert; font-size: revert }`. Tests cover `li > p` in every translated/fallback combination. `<html lang>` is not changed.
- **Dynamic content:** a `MutationObserver` on `document.body` with `characterData`, `childList` and `subtree`:
  - text value changed by the host (differs from what the widget last wrote) → re-extract that block;
  - text nodes replaced or blocks added (framework re-render, SPA route change, lazy lists) → debounced (proposed 300 ms) re-extraction of the affected blocks, batched into the next request;
  - mutations the widget made itself are ignored by comparing against last-written values;
  - toggle-back skips blocks whose original text nodes are gone (the host already re-rendered them in English).
  Blocks below the fold are requested when they approach the viewport (`IntersectionObserver`).
- **Requests and fail open (NFR-410):** each pass sends one batched request per up to N blocks (proposed 50) in viewport order; each response is applied as it arrives, so blocks become Dzongkha chunk by chunk, but **a block is never half-translated**. Hard client timeout per request (proposed 3 s, UNNUMBERED). Timeout, network error, non-2xx, malformed JSON, or a per-block `fallback`/`pending_review` status → that block keeps English. `pending_mt` blocks get **one** re-request after a delay (proposed 8 s) while Dzongkha is on; if still pending, they stay English for this page view. The toggle always settles to a final state (worst case about 3 s + 8 s + 3 s); meanwhile the status line shows static "translating" text, never a spinner that can hang.
- **Stale-response guard (FR-140, FR-210):** each block has a generation counter, bumped on every extraction, toggle, or host mutation. A response is applied only if Dzongkha is still on, the generation matches, the block's text nodes are the same `Text` objects, their current values equal the source that was sent, and the response's marker structure and run count match the node count (the widget re-checks structure itself before any write). Otherwise the response is discarded and the block re-extracted if still relevant. A vitest covers a fee changing from 500 to 600 mid-flight and a toggle-back before a response lands.
- **Config (FR-510):** on load the widget calls `GET /v1/config?origin=…` (short max-age, versioned), which returns the origin's Tier 1 CSS selectors and feature switches. **If config is unavailable, the widget does not offer translation** (page stays English, NFR-410), because a widget without selectors could send Tier 1 content as Tier 2. The `path` sent is `location.pathname` only (no query, no fragment), re-read at every extraction so SPA route changes are respected.
- **NFR-410 interpretation (needs SRS owner confirmation):** "never a partial translation" is read as *per block*: a page may mix Dzongkha blocks with English blocks, but no block is ever partly translated. If the SRS means per page, the widget must hold all writes until every visible block is `translated`, which with async misses means most first visits stay fully English.
- **Build:** "no build step" is read as no bundler or framework. The allowed release step is `tsc` emit, a minifier, and a script that writes the content-hashed file name and SRI hash. UNNUMBERED; confirm against the SRS.
- **Budget:** CI fails if `gzip -9` size ≥ 15 KB. Performance check on a low-end Android profile (throttled CPU 6×, slow 4G): toggle-to-rendered for a fully cached page ≤ 1 s (proposed, UNNUMBERED).

### Phase 1: Orchestrator (`orchestrator/`)

**API: `POST /v1/translate`**

```json
{ "origin": "https://portal.example.gov.bt",
  "path": "/services/renewal",
  "blocks": [ { "id": "b17", "tier": 2, "text": "Pay ⟦t1⟧Nu. 500⟦/t1⟧ at the counter." } ] }
```
Response per block: `{ "id", "status": "translated" | "pending_mt" | "pending_review" | "fallback", "text"?, "reason"? }` plus `{ "model_version", "glossary_version" }`.

- **Request hardening (UNNUMBERED):** `Origin` header must be in the origin allowlist and equal the body `origin`; CORS responds only to allowlisted origins. Limits on blocks per request, characters per block and per request; per-origin and per-client-IP rate limits. The server never dereferences `origin`, `path`, or any URL found in text; they are stored as metadata only (no SSRF path).
- **Personal data (UNNUMBERED; repo rule on citizen data):** the pilot covers **public, unauthenticated pages only**; the widget does not run on pages marked `data-dz-private`, and portal authors mark personal regions `data-dz-skip`. The server normalizes `path` by replacing numeric and ID-like segments with `:id` before storing. Tier 2 segments are not persisted or enqueued for MT until seen from at least N distinct clients (proposed 3, counted with a salted, daily-rotated client hash in Redis), so one-off personalized strings never reach WSO2, TM, or the review UI. Final policy goes to `/cso` (Open Question 15).
- **Tier authority (FR-510):** the server decides the effective tier. Each allowlisted origin has a server-side **tier rule set** maintained by admins: path patterns and CSS selectors that are Tier 1 (selectors delivered to the widget via `GET /v1/config`; path patterns enforced server-side on the normalized `path`). Effective tier = max(client `tier` hint, server rule). A client can raise a block to Tier 1 but never lower one. For the pilot portal, the rule set is filled before launch from the Phase 0 snapshots (fee, eligibility and legal pages). Review-item creation is rate-limited and capped per origin per day, so forged `tier: 1` requests cannot flood the queue.
- **Pipeline (`orchestrator/pipeline/`, guarded):**
  1. **Parse tags:** validate the incoming marker structure (well-formed, balanced, delimiters escaped); reject malformed input as `fallback`.
  2. **Mask entities (FR-140):** ordered pattern set (URLs, emails, citizen IDs, file reference numbers, currency amounts incl. `Nu.`/`BTN`, dates, numbers). Bhutan-specific ID and file-reference patterns maintained as versioned data (`masker_version`) with tests, sourced from `synthetic-entities.json`. The result is `masked_source` plus a per-request **entity map** (placeholder → exact source bytes). No Unicode normalization of source bytes.
  3. **Canonical hash:** `source_hash = sha256(masked_source)`. This one hash is used everywhere: TM rows, review items, jobs, fallback markers.
  4. **Glossary fingerprint:** `gfp = sha256(sorted (term_id, term_version) pairs for glossary terms matched in the English source)`. This meets "cache keys include glossary version" (FR-150) per term rather than globally.
  5. **Two keys, two lookups:**
     - **Approved key** = `(source_hash, lang_pair, masker_version, gfp)`. Approved translations serve **every tier**, so a human-approved Tier 1 translation is reused for identical Tier 2 text.
     - **Machine key** = approved key + `model_version`. Machine translations serve **Tier 2 only**.
     - Lookup order: Redis(approved) → Postgres(approved) → Tier 2 only: Redis(machine) → Postgres(machine). A Postgres index `term_id → keys` lets a glossary change find and purge exactly the affected Redis and TM entries.
     - **TM rows and cache values store masked target text only; they never contain real entity values.**
  6. **Tier 1 miss:** return `pending_review`; upsert a review item keyed by `source_hash`. The **citizen-serving path** (`/v1/translate` → pipeline → job enqueue) has no route to MT for Tier 1: the tier gate raises before enqueue, and a test asserts it (FR-510).
  7. **Tier 2 miss:** return `pending_mt`; enqueue an MT job (deduplicated by MT key).
  8. **Hit:** unmask the stored masked target using **this request's** entity map; verify every placeholder is restored exactly once with byte-identical values; return `translated`. A hit that fails verification is purged and treated as a miss. (So "Pay Nu. 500" and "Pay Nu. 600" share one TM row and each gets its own amount back.)
- **Versions and invalidation (FR-150):**
  - `model_version` comes from deployment config pinned alongside the WSO2 endpoint (the adapter also reads a version header if WSO2 exposes one, and refuses to run if they disagree). UNNUMBERED.
  - **Glossary mechanism:** the glossary is enforced by post-translation checks, not model constraints: for each glossary source term present in the English, the approved Dzongkha term must appear in the output, or the block falls back (cause: *glossary term missing*). Each TM row stores the glossary term IDs it matched.
  - A glossary term change alters `gfp` only for sources containing that term, so it invalidates **only rows that matched a changed term**: machine rows are deleted from cache and TM and re-enqueued through a throttled re-warm (bounded jobs per minute); approved rows move to `needs_recheck` and **stop being served** (Tier 1 returns `pending_review`) until re-approved. This follows invariant 6 literally.
  - Approved rows are not keyed by model version, so a model upgrade keeps human work; machine rows are, so a model upgrade invalidates them, again with a throttled re-warm.
  - **Masker changes:** a `masker_version` bump runs a migration over approved translations: the new masker runs on each stored `masked_source`, treating existing placeholders as opaque. Unchanged text → re-key to the new `source_hash`/`masker_version`. New entities detected, or a removed/narrowed pattern that would no longer produce an existing placeholder → `needs_recheck`. Machine rows are not migrated: their keys miss and they are re-warmed with throttling. Tests cover widened, narrowed and new patterns.

### Phase 1: MT worker and WSO2 adapter

- Jobs table in PostgreSQL (`FOR UPDATE SKIP LOCKED`), unique on cache key. Durable across restarts and visible to audit. Redis stays a pure cache. UNNUMBERED.
- Adapter: OAuth token caching/refresh for WSO2, bounded concurrency, per-call timeout, retry with jittered backoff on 429/5xx, circuit breaker (open → jobs wait, widget keeps English). Batches blocks where the upstream allows.
- After MT: strip any U+200B/U+200C/U+FEFF from model output (FR-160, FR-330) → **validate** placeholders (Premise 4 rules, slot-less positions) → leak scan (no digits, ID patterns, emails or URLs outside placeholders) → glossary check → store the **masked** target as a TM row (`machine`) + Redis. Entity values are never stored in TM or cache; they are restored per request at serve time. Validation failure → store a `fallback` marker with cause (short TTL) so the same block is not retried every page view, and increment the cause counter.

### Phase 1: Review queue, reviewer UI, corpus export

- **Data model:** `translation_versions` is immutable (masked source, masked target, reviewer, time, glossary fingerprint, masker version); `review_items` is mutable (`source_hash`, current key, state, pointer to current approved version). Re-keying and state changes touch only `review_items`.
- **States:** `pending_review → approved | rejected`; `approved → needs_recheck` (glossary term change or masker migration); `needs_recheck → approved` (new or re-confirmed version) `| rejected`. In `needs_recheck` the reviewer sees the previous approved text plus the glossary/masker diff that triggered it. `rejected` behaves like `pending_review` for citizens (English + notice) and is reopened only by explicit reviewer/admin action, never by traffic.
- Reviewer UI: small server-rendered FastAPI + Jinja2 app with autoescaping on, CSRF protection, strict CSP. Shows English source with entity placeholders highlighted, glossary hits, and the page path(s) where the segment appeared.
- **Reviewer MT suggestion (FR-510 boundary):** a separate module, callable only from authenticated reviewer routes, that calls the WSO2 adapter and returns a draft to the reviewer's screen. It writes nothing to cache, TM or jobs, and is not importable from the `/v1/translate` path (enforced by an import-boundary test). FR-510 governs what citizens are served; a reviewer drafting from MT and then approving is human-approved content. The editor refuses to save if entity placeholders are missing, duplicated, or altered, and if tag placeholders are out of order.
- Authentication: GovTech identity provider (Open Question 6). Two roles: `reviewer`, `admin` (glossary, allowlist).
- Audit log (Postgres, append-only): approvals, rejections, edits, glossary changes, allowlist changes, with actor and timestamp.
- Corpus readiness (v1): approved TM rows carry provenance (reviewer, approval time, glossary version, masker version, source page paths), so a corpus can be produced later without data loss. **The export CLI (versioned JSONL/TMX) is deferred until the publication decision (Open Question 9)**, to avoid building an output nobody is yet allowed to use.

### Observability (UNNUMBERED)

Counters, without citizen content in logs: requests, cache/TM hit rate, `pending_mt`/`pending_review`/`fallback` rates by cause and by origin, upstream latency/error rate, breaker state, review queue depth and age. Logged segment text limited to source hashes.
